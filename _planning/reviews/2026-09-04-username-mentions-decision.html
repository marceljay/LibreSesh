Usernames & mentions — a decision

First-cut mentions have shipped (a comment author links to a profile; @username in a comment links too). This page is only about what a username is allowed to be, and how that shapes mentions. Pick with your eyes; tell me the letter.

Where things stand today

ThingNow
Username schema trimmed(40) — any non-empty text ≤ 40 chars. Spaces, emoji, punctuation all allowed. No separate "handle".
Uniqueness One name per event (migration 009), case-sensitive — so "Ada" and "ada" are two different people.
Mention target The free-form name itself, resolved against the set of names the event actually holds.
Prod reality Live events already contain usernames with emoji. Any rule must survive names that already exist.

Do emoji or spaces break mentions? No.

The tokenizer matches against real names in the event, not a character pattern. So @🎉party links if 🎉party is a real username, and @Ada Lovelace links if that exact name exists (it takes the longest matching name). The only character rule is for boundaries — “is this the start of a word” — never for what a name may contain. “Allow emoji” and “resolve mentions” do not fight.

The case-sensitivity point — narrow, and separate from special characters

This is not “restrict letter-case but allow other symbols.” It is one question: may two names that differ only in capitalisation both exist?

Today yes (uniqueness is case-sensitive), but the mention matcher is case-insensitive — so @ada matches both “Ada” and “ada”. If both exist, the mention is ambiguous. Emoji and every other character are irrelevant here; it is only letter-case. Two ways to make the halves agree:

FixEffectCost
Match case-sensitively @ada links only to “ada”, never “Ada”. None, but you must type exact case (awkward on autocapitalising phones).
Fold case for uniqueness (COLLATE NOCASE) “Ada” and “ada” can’t both be claimed; matching stays forgiving. Small migration; check no live event already has a colliding pair.

Recommendation: fold case for uniqueness. It restricts nothing about emoji or symbols, and case-collision is a latent bug regardless of mentions.

The bigger choice: free-form name, or a handle?

How each option handles the same three names, and what a mention looks like.

Username A · Free-form (shipped) B · Restricted handle C · Autocomplete picker
Ada Lovelace @Ada Lovelace (type exact, or pick) @ada_lovelace (handle) type @ada…, choose from list → inserts a resolved link
🎉party @🎉party (works) needs a derived ASCII handle — emoji can’t be a handle type @par…, choose → works, emoji never parsed
Ada / ada ambiguous unless case is folded (see above) handles are unique + folded → no collision no ambiguity — you pick the actual person
Recommended now

A · Leave free-form

What already shipped. Names stay human; resolve against the directory.

  • No migration, no new concept
  • Emoji prod names keep working
  • Fits the app’s account-free ethos
  • A freely typed multi-word name is fragile (needs exact spelling)
Suggest skip

B · Add a handle

A restricted @handle beside the display name; mention by handle.

  • Unambiguous to parse (industry norm)
  • Reintroduces the account/handle concept the app avoids
  • Migration; an emoji-only name has no handle without deriving one
  • A second thing to explain to organisers
Recommended later

C · Autocomplete picker

No grammar change: the composer inserts a resolved mention.

  • Best UX; whitespace/emoji never enter the parse
  • Pairs with the server-side parse that notifications need
  • Depends on composer work (after form-overhaul Phase 2)
  • Not a first-cut item — lands with delivery

My recommendation, in one line

A now, C later, skip B — keep names free-form (respects the emoji names already in prod and the app’s ethos), fold case for uniqueness to kill the one real ambiguity, and add the autocomplete (C) when notifications land, not before.
